# Локации (location_processing)

Дополнительная функциональность этапа 3: администратор задаёт именованные точки
интереса (город, театр, концертный зал — координаты + радиус), а любой
пользователь может найти опубликованные события, которые проходят в пределах
конкретной локации.

Координаты самих событий (`location` в `NewEventDto`/`EventFullDto`) не
меняются и ничем не ограничены — локации это отдельный, не обязательный слой
поверх существующих событий, а не новый способ их создавать.

## API

### Admin — управление справочником локаций

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| `POST` | `/admin/locations` | `NewLocationDto` | `201` `NamedLocationDto` |
| `PATCH` | `/admin/locations/{locationId}` | `UpdateLocationDto` (все поля опциональны) | `200` `NamedLocationDto` |
| `DELETE` | `/admin/locations/{locationId}` | — | `204` |

Пример тела запроса `POST /admin/locations`:

```json
{
  "name": "Большой театр",
  "lat": 55.7601,
  "lon": 37.6186,
  "radius": 5
}
```
`radius` — в километрах, должен быть положительным (`400`, если нет).

### Public — просмотр и поиск

| Метод | Путь | Параметры | Ответ |
|---|---|---|---|
| `GET` | `/locations` | `from`, `size` | `200` `List<NamedLocationDto>` |
| `GET` | `/locations/{locationId}` | — | `200` `NamedLocationDto` / `404` |
| `GET` | `/locations/{locationId}/events` | `from`, `size` | `200` `List<EventShortDto>` / `404` |

`GET /locations/{id}/events` возвращает только **опубликованные** события,
чей `location` попадает в радиус этой локации, отсортированные по дате.
`confirmedRequests` и `views` считаются так же, как и на остальных
публичных эндпоинтах — батчем, без N+1.

## Как считается расстояние

Используется PL/pgSQL-функция `distance(lat1, lon1, lat2, lon2)` — сферический
закон косинусов, результат в км (реализация — из методички курса). Вызывается
из нативного запроса в `EventRepository`:

```sql
SELECT * FROM events e
WHERE e.state = 'PUBLISHED'
  AND distance(:lat, :lon, e.lat, e.lon) <= :radius
ORDER BY e.event_date
```

### Почему функция лежит в отдельном файле

`distance()` — синтаксис `LANGUAGE PLPGSQL`, специфичный для PostgreSQL. Он
живёт в `src/main/resources/schema-postgres.sql` и подключается **только** в
боевом профиле (`application.yml → spring.sql.init.schema-locations`).
Тестовый профиль (`application-test.yml`, H2) намеренно грузит только базовый
`schema.sql` — без функции, потому что H2 такой синтаксис не поддерживает.

Отсюда прямое следствие для тестов:

- **JUnit** (`MainServiceHappyPathTest.locationCrud`) покрывает весь CRUD
  локаций (создание, список, получение, изменение, удаление, валидация,
    404) — это обычный SQL, портируемый между H2 и Postgres.
- **Postman** (`postman/feature.json`) — единственное место, где реально
  проверяется поиск событий в радиусе, потому что для этого нужен настоящий
  Postgres с загруженной функцией `distance()`. Коллекция создаёт два
  события (одно в 1 км от локации, другое — в другой части света) и
  проверяет, что в выдачу попадает только ближнее.

## Схема БД

```sql
CREATE TABLE IF NOT EXISTS locations (
    id     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name   VARCHAR(255) NOT NULL,
    lat    DOUBLE PRECISION NOT NULL,
    lon    DOUBLE PRECISION NOT NULL,
    radius DOUBLE PRECISION NOT NULL
);
```
Таблица не связана внешним ключом с `events` — соответствие вычисляется на
лету через `distance()`, а не хранится.

## Структура кода

```
ru.practicum.location
├── model/NamedLocation.java          — сущность
├── dto/NewLocationDto.java           — создание (admin)
├── dto/UpdateLocationDto.java        — частичное обновление (admin)
├── dto/NamedLocationDto.java         — ответ (public + admin)
├── mapper/LocationMapper.java
├── repository/NamedLocationRepository.java
├── service/LocationService.java
├── service/LocationServiceImpl.java
├── controller/AdminLocationController.java
└── controller/PublicLocationController.java
```
Поиск событий в радиусе не выделен в отдельный репозиторий — метод
`findPublishedEventsWithinRadius(...)` живёт в уже существующем
`EventRepository`, рядом с остальными запросами по событиям.

Класс `NamedLocationDto` назван так специально: в проекте уже был
`ru.practicum.event.dto.LocationDto` (координаты события из старого ТЗ) — во
избежание путаницы двух одноимённых DTO в разных пакетах.
